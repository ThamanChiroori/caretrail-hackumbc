Shared specification (SPEC.md)
Purpose and boundaries
CareTrail is an iPhone-first web app that helps a person remember and explain what happened between medical appointments. A person can record events, medication courses, and label photos; later they can print a chronological report for a clinician. The entries are patient-reported, and the app does not diagnose, identify medication from a photo, attribute a symptom to a drug, check interactions, suggest doses, or decide whether medical attention is needed.
This is a hackathon prototype, not a dependable medical record. Use fictional data only. Do not add accounts, cloud sync, a server, analytics, an AI medical feature, OCR, reminders, or a custom voice-input feature. The iPhone keyboard's dictation is sufficient for optional text fields.
Platform and storage
Build a mobile-first static website with HTML, CSS, and vanilla JavaScript ES modules. It must run in iPhone Safari and, after deployment to an HTTPS URL, be usable from an iPhone Home Screen icon. Avoid a framework, build step, API keys, and backend. Store small structured records in localStorage and optional label images in IndexedDB on that device. A browser's storage can be cleared or lost; data does not sync across devices. Do not imply otherwise. The first iPhone test should save one record and one photo, close the app, reopen it in the same Safari or Home Screen context, and confirm they persist. Do not mix contexts during the demo.
Screens and behavior
1. Profile. Fields: name, date of birth, optional sex, optional blood group (including “Unknown”), allergies (including “Unknown” or “Not entered”), and additional information. No field should prevent a person from recording an event. Calculate age from date of birth at report time; do not store a stale age. Keep the profile after starting a new visit record. Show missing information honestly rather than treating it as a negative finding. A patient can edit their profile at any time.
2. Events. At the top, show a prominent “Add event” button. Under it, show previous events as large, tappable cards in chronological order. Types are symptom, injury, possible reaction, consultation, medication taken, and other. An event may contain a description, an optional linked medication, and an optional dose note for “medication taken.” Every event automatically receives an immutable createdAt timestamp when first saved. An optional occurredAt records when the event happened; it defaults to blank and can be supplied or corrected later. If blank, show “When it happened: not entered” and place it in the timeline by createdAt. Show “Recorded at” separately. Editing must never overwrite createdAt. Permit editing and deleting an event. Do not create a medical interpretation from its type or timing. An event with only its automatically recorded time is valid; its card says “No details entered.”
3. Medications. At the top, show a prominent “Add medication” button. The primary flow asks the person to take or choose a clear photograph of the printed bottle label. The screen says: “Try to include the medication name on the label. Check that it is readable before saving.” Preview the photo at a useful size and offer “Retake photo.” The photo is the primary identifier; entering a name or familiar nickname is optional. Give a visible “Add photo later” path for camera failure or when the bottle is unavailable. Such cards must prominently say “Photo needed” and make adding or replacing the image easy. Never infer a drug name from its photo. If no name is entered, use a stable card label such as “Medication photo 1 — name not entered” (or “Medication 1 — photo needed”). Labels must remain stable across a reload and in the report; do not renumber based on sorting.
For the start date, offer a large “Starting today” action that records the local calendar date, plus a smaller “Choose another start date” option. If the person does not know the start date, allow “Date not entered” rather than fabricating a date. The medication card list emphasizes ongoing medications and shows a large clear photo, optional name/nickname, start date, and status. Tapping a card opens the details, where the user can change the photo or details and choose “Finished bottle” or “Stopped taking.” Each records an end date (today by default, editable) and a distinct completion reason. Permit editing a mistaken completion and deleting a card with confirmation. Completed medications remain visible in a separate section until the next visit record is cleared. A medication entry may exist with neither photo nor name only as a temporary incomplete entry and must display “Photo and name needed”; avoid letting an unidentifiable entry look complete.
The app records a medication course, not every dose automatically. To record an individual dose, add an event of type “medication taken.” No reminder or interaction checker is part of this MVP.
4. Visit report. Preview a clean clinician-facing report showing the profile, report date, current and completed medication courses with start/end dates and completion reason, medium-sized label images where available, and a chronological event list with both “Happened at” (if supplied) and immutable “Recorded at.” If an event's happened time is missing, sort by recorded time and identify it as such. Include optional medicine links and dose notes without making a causal claim. Label missing medication names explicitly. Show “Patient-entered information; not clinically verified.” Never guess missing fields or claim that a medication was taken every day between its start and end dates. The user may print or save a PDF using the browser print dialog. The report must remain readable if a photo fails to load and when it spans multiple pages.
New-visit record and data deletion
Opening or printing a report must never delete records. Flow: preview → tap “Print / Save report” → the user checks that a copy exists → tap “Start new visit record” → a separate confirmation lists what will be cleared and what will stay. The browser cannot verify printing or saving, so do not say it did. Clearing removes current events, completed medication courses, and only photos that belonged solely to those deleted courses. Keep the profile and ongoing medication courses, their original start dates, and their photos. Make the reset deliberate and describe the loss as irreversible. The app must not promise that a PDF alone is a complete or secure backup.
Data contract
Use ISO strings for timestamps (new Date().toISOString()), local YYYY-MM-DD strings for calendar dates, and local formatting for display. Use stable crypto.randomUUID() identifiers with a fallback. Escape user-entered content before placing it into HTML.
Profile = {
  name: string, dateOfBirth: string, sex: string, bloodGroup: string,
  allergies: string, additionalInfo: string
}

Event = {
  id: string, createdAt: string, occurredAt: string | null,
  type: 'symptom' | 'injury' | 'possible_reaction' | 'consultation' | 'medication_taken' | 'other',
  description: string, medicationId: string | null, doseNote: string
}

Medication = {
  id: string, displayNumber: number, name: string, doseText: string,
  startedAt: string | null, endedAt: string | null,
  status: 'ongoing' | 'completed',
  completionReason: 'finished_bottle' | 'stopped_taking' | null,
  photoId: string | null
}
displayNumber is assigned once on creation and is stable. createdAt must be immutable after creation. A blank occurredAt is not an error. A blank medication name is allowed when a photo is available; a blank photo is allowed through the clearly marked fallback. Do not require both. The app may temporarily save a fully incomplete medication card so the user can add details later, but flag it prominently and do not hide that incompleteness in the report.
Module ownership and interfaces
One repository, four branches, one owner for each file. Role 4 creates the minimal shell and SPEC.md first, then hands over index.html and styles.css ownership to Role 1. No one asks an assistant to replace another owner's module.
- Role 1 owns index.html, styles.css, and the on-screen forms/cards design. Required stable element IDs: profile-form, event-form, medication-form, timeline-list, medication-list, report-content, print-report, start-new-record. Include appropriately named fields from the data contract, but Role 4 binds all behavior.
- Role 2 owns storage.js, which provides named async exports: getProfile, saveProfile, listEvents, addEvent, updateEvent, deleteEvent, listMedications, addMedication, updateMedication, deleteMedication, savePhoto, getPhotoBlob, and startNewRecord. savePhoto(file) returns a photo ID; getPhotoBlob(id) returns a Blob or null. addEvent sets createdAt regardless of any input and updateEvent preserves the old createdAt. addMedication assigns a stable displayNumber. startNewRecord obeys the retention rules above. Return friendly errors on storage failure.
- Role 3 owns report.js and report.css, exporting renderReport({profile, events, medications, photoUrls}, mountElement) and printReport(). photoUrls is an object keyed by photoId, supplied by Role 4 after resolving photos; values are temporary object URLs. The report module reads no storage and deletes nothing. Role 4 revokes object URLs when appropriate. Print styles hide all app controls and keep medium images with their medication entries.
- Role 4 owns app.js, README.md, integration, testing, hosting, and submission. It connects the other modules, handles photo previews and object URL cleanup, forms, navigation, edit/delete, print, reset confirmation, and accessible save/error messages.
Accessibility requirements for MVP
Use visible text labels, large readable type, high contrast, and generous spacing. Make all primary controls at least about 44 × 44 CSS pixels, and test with iPhone larger text. Do not convey status by color alone. No swipe-only or long-press-only actions. Every photo card has descriptive accessible text such as “Medication photo 2, name not entered, started September 26, ongoing”; a photo by itself is not an adequate screen-reader label. Allow the optional name/nickname to be filled with the iPhone keyboard's dictation. Show large photo previews, “Retake photo,” “Add photo later,” and clear photo quality instructions. Show confirmations such as “Event saved” and specific errors such as “Photo couldn't be saved; try again or add it later.” Keep entered form data when a save fails. Add a visible confirmation before deletion or reset. Check the app with VoiceOver if time permits; do not claim full accessibility compliance without testing.
MVP acceptance test, on one actual iPhone
1. Save a fictional profile and reopen the same app context; the profile remains.
2. Add one medication by taking a clear label photo and tapping “Starting today.” Leave the name blank. Reopen the app; its large photo and stable unnamed label remain.
3. Add a second medication via “Add photo later.” Later open its card, add a photo or optional name, and confirm the card updates without losing its start date.
4. Add an event with no happened time, then another with a happened time. Edit both. Their “Recorded at” values never change, while “Happened at” can change.
5. Mark one medication “Finished bottle” and another “Stopped taking”; their end dates and distinct reasons appear in the preview and a legible printed/saved report with medium photos.
6. Create an ongoing medication. After viewing and printing a report, explicitly start a new visit record. Old events and completed medications disappear; the profile and ongoing medication, including its photo and original start date, remain.
If photos prove unreliable, fix them before visual polish. If still blocked, demonstrate the clear “Add photo later” state and explain the known limitation; never claim photo persistence works without testing. Prioritize a correct report and safe reset over any stretch feature.
